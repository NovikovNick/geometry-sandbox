DSL-based animation system

Хоть анимации по сути это простой процесс lerp, но правильно прикрутить это к приложению та еще задачка.

using namespace std::chrono;
animation::KeyframeCollection keyframes;
keyframes += keyframe(0s)
| accessor::point(pointId) / point::position << Vec3{0, 0, 1}
| accessor::point(pointId) / point::color << Color::blue();
keyframes += keyframe(1s)
| accessor::point(pointId) / point::position << key(Vec3{0, 0, 1}, circularMovement)
| accessor::point(pointId) / point::color << Color::red();
animation::Manager manager;
animation::Clip clip = manager.build(keyframes);
clip.loop = true;
animation::Handle handle; // id, version
handle = manager.play(clip); // starts animation::Instance

построена на трёхуровневой модели абстракции, разделяющей пользовательский интерфейс, внутреннее представление данных и непосредственно анимируемые свойства. Это позволяет совместить выразительный, безопасный на этапе компиляции DSL с высокопроизводительным рантаймом, лишённым виртуальных вызовов и шаблонной магии.

1.1. Слои абстракции

Слой namespace Назначение
Frontend classes gsand::frontend Классический ООП-интерфейс для пользователя. Оперирует объектами сцены (Point, Line и т.д.), скрывая ECS-представление. DSL анимационной системы работает именно с этими классами.
Entry classes gsand::ecs::component, gsand::ui ECS-компоненты со стандартным layout (standard layout type). Идентифицируются по уникальному id. Анимационная система работает с ними как с сырыми байтами (std::span<std::byte>).
Property classes Вложены в entry classes Непосредственно анимируемые поля внутри entry-классов (Vec3, Color, float и т.д.).

Подсистема рефлексии, хранит offset в байтах для property типов внутри entry типа, а также соответствие между frontend, entry и проперти типами. Данные хранятся в виде плоского дерева для удобства поиска root frontend типа и property потомков, а также random access по id.

1.2. Подсистема рефлексии

Отдельная подсистема хранит метаинформацию о связях между слоями:

  • Соответствие frontend class → entry class
  • Соответствие property class → родительский entry class
  • Смещение (offset) каждого property-поля относительно начала entry-класса

Данные хранятся в памяти в виде плоского дерева (flat tree) — иерархия представлена линейным массивом узлов, где связи задаются числовыми индексами родителей, а не указателями. Это обеспечивает кэш-френдли доступ, быстрый расчёт суммарных смещений и простоту сериализации.

2. DSL анимационной системы

DSL спроектирован так, чтобы гарантировать корректность описания анимации на этапе компиляции. Ошибки в именах свойств, типах значений или несовместимость интерполяторов выявляются до запуска программы.

2.1. Базовый синтаксис

using namespace std::chrono;
using namespace algovis::dsl;
AnimationParams animation;
animation.loop = true;
animation += keyframe(0s)
| accessor::point(pointId) / point::position << Vec3{0, 0, 1}
| accessor::point(pointId) / point::color << Color::blue();
animation += keyframe(1s)
| accessor::point(pointId) / point::position << val(Vec3{0, 0, 1}, circularMovement)
| accessor::point(pointId) / point::color << Color::red();
animManager.add(std::move(animation));

3. Механизм анимации в рантайме

3.1. Прямая байтовая запись

При проигрывании анимации система не использует виртуальные вызовы и не инстанцирует шаблоны для каждого типа свойства. Вместо этого:

  1. При компиляции/инициализации DSL-выражения вычисляется итоговое смещение целевого property-поля относительно начала entry-компонента (суммированием смещений по плоскому дереву рефлексии).
  2. В рантайме система получает void* на экземпляр entry-компонента.
  3. Прибавляет заранее вычисленное смещение.
  4. Записывает интерполированное значение через memcpy.

Это минимизирует накладные расходы и сохраняет предсказуемую производительность при анимации сотен свойств за кадр.

4. Пример полного цикла использования

// 1. Создание объекта через frontend-интерфейс
entt::entity pointId = sceneService.addPoint({
.color = Color::blue(),
.radius = 0.08F
});
// 2. Определение пользовательского интерполятора
Interpolator<Vec3> circularMovement = [](const Vec3&, const Vec3&, float t) -> Vec3 {
constexpr float angleRad = 360.0f * std::numbers::pi / 180;
return Vec3{std::sinf(angleRad * t), 0, std::cosf(angleRad * t)};
};
// 3. Описание анимации на DSL
AnimationParams animation;
animation.loop = true;
animation += keyframe(0s)
| accessor::point(pointId) / point::position << Vec3{0, 0, 1}
| accessor::point(pointId) / point::color << Color::blue();
animation += keyframe(500ms)
| accessor::point(pointId) / point::color << Color::red();
animation += keyframe(1s)
| accessor::point(pointId) / point::position << val(Vec3{0, 0, 1}, circularMovement)
| accessor::point(pointId) / point::color << Color::blue();
// 4. Добавление в менеджер анимаций
animManager.add(std::move(animation));

5. Ключевые проектные решения

Решение Обоснование
DSL с compile-time валидацией Исключает ошибки в рантайме, сохраняя выразительность
Frontend-классы в DSL Пользователь оперирует привычными объектами, а не ECS-компонентами
Прямая байтовая запись Устраняет виртуальные вызовы и шаблонную сложность
Плоское дерево рефлексии Быстрый расчёт смещений, кэш-френдли доступ, простая сериализация
Стандартный layout entry-классов Гарантирует корректность прямого байтового доступа

Создание своей анимационной системы с DSL с compile-time валидацией продиктовано стремлением совместить предельную гибкость с надёжностью. DSL даёт возможность описывать анимацию ключевыми кадрами или пользовательскими интерполяторами для произвольных полей объектов на любой глубине вложенности. И одновременно гарантирует корректность этого описания ещё на этапе компиляции, не допуская ошибок в рантайме.

using namespace std::chrono;
using namespace algovis::dsl;
entt::entity pointId = sceneService.addPoint({.color = Color::blue(), .radius = 0.08F});
Interpolator<Vec3> circularMovement = [](const Vec3&, const Vec3&, float t) -> Vec3
{
constexpr float angleRad = 360.0f * std::numbers::pi / 180;
return Vec3{std::sinf(angleRad * t), 0, std::cosf(angleRad * t)};
};
AnimationParams animation;
animation.loop = true;
animation += keyframe(0s)
| accessor::point(pointId) / point::position << Vec3{0.0f, 0.0f, 1.f}
| accessor::point(pointId) / point::color << Color::blue();
animation += keyframe(500ms)
| accessor::point(pointId) / point::color << Color::red();
animation += keyframe(1s)
| accessor::point(pointId) / point::position << val(Vec3{0.0f, 0.0f, 1.f}, circularMovement)
| accessor::point(pointId) / point::color << Color::blue();
animManager.add(std::move(animation));

Как приложение в целом, так и анимационная система в частности используют классический ООП-интерфейс на верхнем уровне, в то время как ядро построено на ECS-архитектуре. Подобно тому, как для создания объекта на сцене используется frontend класс, скрывающий внутреннее ECS-представление, DSL анимационной системы оперирует тем же frontend классом, а не ECS компонентами.

Классы ООП-интерфейса верхнего уровня находятся в namespace gsand::frontend и называются frontend classes.

На уровне реализации анимационная система использует механизм прямой байтовой записи в поля целевых объектов. Данный подход позволяет минимизировать как накладные расходы на виртуальные вызовы, так и сложную в сопровождении шаблонную магию.

Все классы, которые хранятся в namespace gsand::ecs::component и namespace gsand::ui, имеют стандартный layout и которые можно идентифицировать по id, называются entry classes. Анимационная система работает с ними как с сырыми байтами.

Все классы, которые находятся внутри entry classes называются как property classes и непосредвенно они и анимируются.

Отдельная подсистема рефлексии, хранит соответствие между frontend, entry и проперти классами, смещение каждого property относительно entry класса. В памяти эти данные хранятся в виде плоского дерева.

struct Property
{
std::uint32_t id; // unique property id
int depth; // depth in entry object
int offset; // offset in entry object
Type entryType;
Type type;
std::string_view name; // to distinguish between fields of the same type
};

Эта метаинформация заполняется в плоское дерево. Где Property 1 уровня это всегда API тип Далее на 2 уровне всегда Entry тип И ниже идут обычные типы вроде Vec3, Color, float

Эти типы никак не пересекаются, т.к. у каждого группы типов своя зона отвественности.

API тип кроме как по кол-ву каналов, никак не связан с Entry типом, который находится непосредственно в памяти.

Подсистема рефликсии должна решать проблему

General classes

algovis::PropertyRegistry - отвечает за иерархию каналов/свойств

  • обход каналов. т.е. по всем анимированным полям сущности включая вложенные
  • запись/чтение из sample, запись/чтение из сущности

Алгоритм

  1. В compile-time собираем мета информацию об анимируемых типах: точки, линии, камеры, кнопки.
  • нужен отступ от составного и простого объектов, чтобы записывать значения.
  • примитивный объект - это просто float. В будущем по идее все, что можно смаппить во float
  • просто объект - это претендент стать ecs::component
  • составной объект - в первую очередь это объект, на который можно повесить отдельную анимацию
  1. Build анимации
  2. При update в manager'е вычисляет progress каждой анимации
  1. Далее при update manager смотрит, какой тип объекта, находит его и отправляет в сэмплер как байтовый массив вместе с ассетом и progress который нужно вычислить
  2. после того как sample готов, он записывается в байтовый массив
  • Для упрощения кода, анимационная система воспринимает анимируемые объекты просто как байтовый массив.
  • Вся информация необходимая для записи собирается в compile-time в DLS модуле.
    • Каждый анимируемый объект регистрируется в системе с указанием AnimatableType
    • система строит плоское дерево всех вложенных анимируемых свойств таргета
    • положение свойства в этом дереве является однозначным идентификатором
